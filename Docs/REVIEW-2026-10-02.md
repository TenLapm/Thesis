## Verdict

**The structure is sound and does not need rebuilding.** The split into a pure
simulation, a thin Unity host and a headless harness is doing what it was meant to:
WP5 proved the same game runs bit-for-bit in Unity and headless, and the dependency
rules are enforced by both compilers.

There are **five problems that will bite in the next packages** if they are not
designed in now, **five decisions that are yours**, and a list of smaller hardening
items. None of them is a reason to stop; most are cheap now and expensive later.

## A. Problems to design in before they bite

### A1. A planner that throws breaks the simulation (shown)

`ARCHITECTURE.md` §6 promises "a participant session never crashes because of the
director". Today a throwing planner corrupts the game state:

- `Simulation.BeginWave` increments `WaveIndex` **before** it calls `PlanWave`. If
  `PlanWave` throws, the number stays incremented and the next tick tries again.
  Shown: a planner that throws three times makes the first real wave **wave 4**.
- If `OnWaveResolved` throws once, **every later tick throws** a
  `NullReferenceException`. The game is dead.
- `SimHost.Update` has no handler, so in Unity this repeats every frame.

Nothing triggers this today (`EscalationPlanner` cannot throw). It matters from WP10.

**Fix (small, do now):**
1. `BeginWave` asks for the plan and validates it *before* changing any state.
2. A `SafePlanner` wrapper (in `Thesis.Director`) catches an exception or an invalid
   plan from the inner planner, returns the escalation plan for that wave, and
   records `fallback`. `DirectorHost` always wraps. This is the fallback §6
   describes, placed where it can actually work.
3. `ValidatePlan` becomes callable from outside `Simulation`, so the wrapper can
   check a plan without throwing inside a tick.

### A2. After the lifetime clock goes, nothing guarantees a wave ends (WP-C1)

The clock is the only thing that makes every enemy resolve today. WP-C1 removes it.
After that an enemy that cannot move stands forever, the wave never resolves (D4
waits for the last agent), and the game soft-locks. Ways to get there:

- `MoveSpeed` 0 is a valid plan today (`ValidatePlan` allows `>= 0`).
- Slow effects: §4.6 keeps "the minimum factor" but sets no floor above 0.
- A map whose spawn cannot reach the core through static geometry.
  `MapData.Validate` does not check this. An agent with no next tile stands still.

Checked: on SampleScene this cannot happen today (0 stuck agent-ticks out of 12.5
million in the 25-wave run), and **no current map has a single static blocker**, so
that code path is only exercised by test fixtures.

**Fix (inside WP-C1):** require `MoveSpeed > 0`; give `SlowFactor` a floor in
config; make `MapData.Validate` check every spawn reaches the core; add a
`MaxWaveSeconds` backstop that force-resolves the stragglers and says so loudly in
telemetry; add a test "every wave resolves within a bound".

### A3. Director maths will not be bit-identical across runtimes (measured)

The explicit-cast rule makes `+ − × ÷ √` agree everywhere. It does nothing for
`log`, `exp` and `pow`, which each runtime takes from a different maths library.

Measured over one million inputs each, Unity (Mono) against .NET 9 on this machine:

| Function | Same bits? |
|---|---|
| `Math.Log`, `Math.Exp`, `Math.Sin`, `Math.Cos`, `Math.Sqrt` | yes |
| **`Math.Pow`** | **no** |

`Log` and `Exp` agree *here*. That is not a guarantee: these come from the C runtime,
whose results can differ by CPU and platform. `Thesis.*` uses none of them yet, so
this is the moment to decide. The code about to need them:

- the Beta sampler (WP7): normal draws and the Marsaglia–Tsang test use `log`;
- the kernel estimator (WP7): Gaussian weights use `exp`;
- entropy features (WP8) and placement entropy (WP6): `log`.

A last-bit difference will almost never change which strategy wins, which is exactly
what makes it dangerous: a divergence that shows up once in thousands of waves.

**Fix (before WP7):** `Thesis.Core.DetMath` with `Log` and `Exp` written from a
fixed algorithm using only basic arithmetic (a port of the classic fdlibm routines is
about 60 lines each). Everything in `Thesis.*` calls those. A test scans the source
and fails on a direct `Math.Log/Exp/Pow/Sin/Cos`. A fingerprint test pins the results
in both test runners.

### A4. A replay cannot reproduce a director session

`ReplayFile` stores the planner's **name**. That is enough for the escalation
planner, which has no state. A director has a config, thresholds, a cost table, an
estimator and three RNG streams, none of which is in the file or in the state hash.
`ARCHITECTURE.md` plans to add an estimator snapshot, but not the rest.

**Fix (WP10–WP11, decide now): record each wave's `WavePlan` in the replay and play
the plans back.**

- Replaying the *simulation* then needs no director at all. It is exact for every
  condition, on every runtime, and stays valid after the director's code changes.
- Checking the *director* becomes a second, separate step (`replay --rerun-director`):
  rebuild it from the stored config and snapshot and compare its plans to the
  recorded ones.
- It also makes telemetry reproducible from a replay (see C6), which protects the
  study data.

Related: `Simulation.Clone(planner)` hands the clone whatever planner it is given. If
that is the live director, the clone and the real run share one estimator and one RNG.
`Counterfactual` (WP12) must give each clone its own planner; say so in §4.4.

### A5. The telemetry golden-file test cannot pass as written (measured)

WP6 requires a run to produce **byte-identical JSONL**, and tests run in both
runners. The JSON library writes the same float differently on the two runtimes:

| Value | .NET 9 | Unity (Mono) |
|---|---|---|
| a budget after many `+0.2` | `0.20000458` | `0.200004578` |
| `1f / 3f` | `0.33333334` | `0.333333343` |
| a `double` third | `0.3333333333333333` | `0.33333333333333331` |

Both read back to the same bits, so replays are unaffected (and the setup hash
checks it). Member order is the same on both. Only the text of some floats differs.

Second cause: the repository has no `.gitattributes` and this machine has
`core.autocrlf=true`, so a committed golden file is checked out with CRLF line ends.

**Fix (WP6):** telemetry writes floats through one formatter in `Thesis.Core.Json`
that gives the same text everywhere; add `.gitattributes` (`* text=auto`, and
`*.jsonl -text`, `*.replay.json -text`).

## B. Decisions that are yours

### B1. Which runtime does the study build use?

`WORKPLAN` treats an IL2CPP player build as an open risk. The project's Windows build
is actually set to **Mono** right now (checked in Player Settings: Windows 64-bit,
Mono, managed stripping off; only Android is set to IL2CPP), and Mono is the runtime
WP5 verified. **Recommendation: decide that the study build is Windows, Mono,
and write it down.** The IL2CPP question then disappears.

Whatever you choose, the check "record in the built player, verify headless" has to
happen **before the pilot**, not before the build freeze: the pilot (break, week B1)
comes first and its data is recorded by a build.

### B2. The primary metric is still undefined (S7), and the proposal is not in the repo

- S7 (what exactly the placement entropy is taken over) is listed as needed by WP6.
  Because replays are exact, the metric can be **recomputed from replays at any
  time**, so S7 need not block the code. It does have to be fixed before the pilot.
- S9 and S10 refer to "the proposal's §6.2 and §6.3". I could not find the proposal
  in the repository. Whoever implements WP8 and WP9 needs those sections.

### B3. Walls can never be removed. Is there room to "rebuild"?

§4.6: "Selling walls: not allowed, same as today." The thesis measures rebuilding,
but the only ways a wall leaves the board are an enemy breach or nothing. In the
25-wave bot run a third of the map (489 of 1,444 tiles) was wall at the end. A bot is
not a person, but the direction is clear: as the board fills, every player in every
condition has fewer choices, which pushes the two conditions together and shrinks
the effect G5 looks for.

Towers are already sellable (`SellTower`), and selling a wall is the same operation.
**Suggestion:** decide in WP-C3 whether walls can be sold or demolished. It is a
game-design call, so it is yours.

### B4. Schedule

The revised plan puts WP6, WP-C1 and WP-C2 before the end of W7. WP0–WP5 are done;
those three are not. If W5 began on 14 September, the plan is about one week behind,
and the plan itself says the W15 reserve is already at risk.

Two things would win time back without cutting scope:
- **Do WP-C1 next and fold WP6 into WP-C3.** Nothing on the path to WP-C1 or WP-C2
  needs telemetry, and schema 1 (the game without towers) will never see a
  participant. Building telemetry once, at schema 2, saves a session.
- **Run WP7 in a parallel session**, as planned. It depends only on WP0 (and on A3).

The plan's own first cut, the Flying class and `flying_bypass`, remains available.

### B5. Every session uses seed 1

`SimHost.seed` is 1 and `randomSeed` is off in SampleScene, so every play and every
restart deals the same pieces. That is right for development. Before the pilot the
build needs a way to set participant, condition and seed per session (WP14 mentions
a "session-condition selector"; S13 is the open question behind it).

## E. Checked and found fine

- **Layering.** Dependencies point one way; `noEngineReferences` and the `dotnet`
  mirror both enforce it. No mutable static state in `Thesis.*`.
- **Determinism core.** PCG streams, tick order, hashing by bit pattern, the cast rule.
  194 tests in both runners; recordings from each runtime replay on the other.
- **JSON member order** is the same on both runtimes.
- **Costs.** A state hash is about 50 µs on both runtimes; `Simulation.Clone` is 0.15 ms
  (.NET) and 0.39 ms (Mono) with 4,000 agents in the list. The five features as
  §5.3 defines them are route walks, not rebuilds, so they sit far inside G2's 16 ms.
  The strategies are not specified yet (S10); one that searches by rebuilding the
  field would have to count its rebuilds at about 1 ms each in Unity.
- **Unity host.** The adapters are thin and hold no rules. Restart reloads the scene
  and the old session's replay is written on the way out.
- **The planner seam and the mutation guard.** One interface for every condition is
  the right shape for the ablation, and the guard has already paid for itself in tests.
- **The order of work** (port faithfully, prove determinism, then change the rules).
  WP4 and WP5 each found a real defect that would have been untraceable otherwise.
